## Зачем эта лекция

Браузер умеет HTML и JS. Данные магазина, вход и заказы живут **на сервере**: метод + путь + тело + код ответа.

На этапе 6 один фронт (`frontend/`) и три бэкенда с одним JSON-контрактом:

| Стек | Запуск | Порт |
| --- | --- | --- |
| PHP | `php -S localhost:8000 router.php` из `php/` | 8000 |
| Django | `python manage.py runserver 8001` из `django/` | 8001 |
| Node.js | `npm start` из `nodejs/` | 8002 |

Сессия — cookie, `fetch` с `credentials: "include"`. Пароль в ответах не отдают. Выбранные товары после логина лежат на сервере, а не только в `localStorage`.

На тесте правильный ответ почти всегда про **смысл метода, кода или заголовка**, а не про SQL JOIN, цвет кнопки и Git.

## 1. Методы: GET, POST, идемпотентность, PUT / PATCH

### GET — чтение без побочек

HTTP GET по смыслу — **безопасное чтение**, без побочных эффектов в идеале. Не создаёт запись, не удаляет ресурс и не открывает SMTP.

```http
GET /api/products HTTP/1.1
Host: localhost:8000
Accept: application/json
```

В Coral: список товаров, один товар, `GET /api/me`, `GET /api/orders`. Повтор того же GET не должен регистрировать пользователя и не класть заказ.

Кэш и закладка работают с GET: URL описывает ресурс. Тело у GET обычно пустое; фильтр — в query (`?q=hat`).

### POST — действие с телом

POST обычно **создаёт или запускает действие** с телом запроса. Не «только скачать файл» и не «запрещён в HTML-формах».

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{"email":"ada@coral.test","password":"secret1"}
```

В Coral POST:

| Путь | Тело | Что делает |
| --- | --- | --- |
| `/api/auth/register` | `{ name, email, password }` | создаёт пользователя и сессию |
| `/api/auth/login` | `{ email, password }` | проверяет пароль, ставит сессию |
| `/api/auth/logout` | — | снимает сессию |
| `/api/orders` | `{ productId }` | добавляет выбранный товар |

Повтор POST регистрации с тем же email — уже не «ещё один успех», а конфликт (409). Поэтому POST **не** считают идемпотентным.

### Идемпотентность

Повтор даёт **тот же эффект**. В идеале так себя ведут PUT и DELETE: второй PUT с тем же телом оставляет ресурс в том же состоянии, второй DELETE «уже нет» — тоже 404/200, без второй потери данных.

Не «запрос нельзя повторить» и не «только POST идемпотентен». POST как раз часто неидемпотентен: две оплаты — два списания.

GET безопасен *и* идемпотентен. PUT идемпотентен, но не обязан быть «безопасным» (он меняет данные, просто повтор не удваивает эффект).

### PUT vs PATCH

**PUT** часто полная замена ресурса: прислали весь объект. **PATCH** — частичная: только изменённые поля. Не синонимы RFC; PATCH не «удаляет ресурс»; PUT не «только для картинок».

```http
PUT   /api/users/3   {"name":"Ada","email":"ada@coral.test"}
PATCH /api/users/3   {"name":"Ada Lovelace"}
```

В учебном API Coral обновление пользователя не вынесено: заказы добавляют POST. На тесте спрашивают общий смысл пары PUT/PATCH.

**На тесте:** GET, POST, идемпотентность, PUT vs PATCH.

## 2. Коды ответа

Код — короткая сводка, тело уточняет. Клиент Coral смотрит и HTTP-статус, и `{ "ok": true/false }`.

### 2xx — получилось

**200** — успех. Список товаров, логин, `GET /api/me`. Не «ресурс создан» (это ближе к 201) и не «нет прав».

**201** — **ресурс создан**. В учебниках POST `/users` отвечает 201 и заголовком `Location`. В контракте Coral успешное создание часто тоже 200 + `{ ok: true, data }` — это упрощение учебного JSON, а не отмена смысла 201.

### 4xx — виноват клиент

**400** — **некорректный запрос клиента**: короткое имя, пароль короче 6, битый JSON. Не «нет сети» и не таймаут DNS.

```json
{ "ok": false, "error": "Invalid registration data" }
```

**401** — **нужна аутентификация**: нет сессии или неверный пароль. `GET /api/me` и `POST /api/orders` без cookie. Не путать с «файл слишком большой».

**403** — **вошёл, но нет прав**. Пользователь известен, действие запрещено (не админ, чужой заказ). Это не «то же, что 401 всегда». 401 = «кто ты?», 403 = «знаем кто, нельзя». На этапе 6 в Coral 403 почти не задействован — идея понадобится в админке.

**404** — **ресурс не найден**: `GET /api/products/no-such-id`, неизвестный путь. Не конфликт уникальности и не CSRF.

**409** — **конфликт**. В Coral регистрация на занятый email:

```json
{ "ok": false, "error": "Email already registered" }
```

Повторный уникальный ключ, конфликт версий — тот же класс.

### 5xx — виноват сервер

**500** — **ошибка сервера**: необработанное исключение, упала БД. Клиент запрос мог прислать правильный. Не «не найден клиент» и не CORS preflight.

Статику PHP-роутер Coral при неизвестном файле тоже отдаёт 404, не 500. 500 оставляют для «у нас сломалось».

| Код | История Coral |
| --- | --- |
| 200 | `GET /api/products` — каталог |
| 201 | «пользователь создан» в учебнике REST |
| 400 | пароль `123` при регистрации |
| 401 | Select product без входа; неверный пароль |
| 403 | вошёл как покупатель, просит админский путь |
| 404 | товар с выдуманным id |
| 409 | второй раз тот же email |
| 500 | необработанный throw в обработчике |

**На тесте:** 200, 201, 400, 401, 403, 404, 409, 500.

## 3. Контракт, маршруты, статика, три стека

### Существительные `/users`

REST-ресурс часто именуют **существительными во множественном числе**: `/users`, `/products`, `/orders`. Не глаголами `/doGet`, не случайным хешем и не номером порта.

Действие — HTTP-метод:

```text
GET    /api/products       список
GET    /api/products/:id   один товар
POST   /api/orders         добавить выбор
GET    /api/orders         список выбора
POST   /api/auth/login     вход (глагол в auth — исключение «сессия», не ресурс каталога)
```

### `Content-Type: application/json`

JSON в теле обычно с заголовком **`Content-Type: application/json`**. Не `Accept: image/png` как единственный, не `Cookie: json`.

```js
headers["Content-Type"] = "application/json";
init.body = JSON.stringify(config.body);
```

Сервер Coral отвечает тем же:

```php
header('Content-Type: application/json; charset=utf-8');
```

Клиент ставит `Accept: application/json`. Картинке — `image/jpeg`, CSS — `text/css`. Путать типы — частая причина «JSON.parse упал на HTML».

### Статический файл

CSS, картинку, `index.html` сервер отдаёт **по пути из файловой системы с Content-Type**. Не через SQL SELECT, не WebRTC и не email.

В `php/router.php`: путь `/` → `frontend/index.html`, `/css/style.css` → файл, `/assets/...` → корневые `assets/`. Тип угадывают по расширению. Нет файла — 404.

API и статика в Coral живут на одном origin: браузер грузит страницу с `:8000` и ходит на `/api/...` без CORS.

### Маршрутизация

Выбор обработчика по **method + path**. Не выбор шрифта и не нормализация БД.

```php
if ($method === 'GET' && $path === '/api/products') {
    send_json(load_products());
}
if ($method === 'POST' && $path === '/api/auth/login') { /* … */ }
```

Один путь, разные методы — разные действия. `GET /api/orders` читает, `POST /api/orders` пишет. Не найдено — 404.

### Query `?q=hat`

Часть URL для параметров, **чаще у GET**. Не тело POST, не заголовок Host и не сертификат.

```text
GET /api/products?q=hat
```

Поиск «hat» можно заложить в закладку и отправить ссылкой. Пароль в query не кладут: URL светится в логах и истории.

### PHP, Django, Node — один контракт

Сравнимы, потому что **все принимают HTTP и отдают JSON**. Это не один язык. Все трое в эталоне умеют сессии и файлы.

Фронт один: `frontend/js/api.js`. Сменили порт — тот же `POST /api/auth/login`, те же коды. На занятии начинают с PHP (прямой HTTP), затем Django и Node.

### Таймаут

**Прерывание слишком долгого ожидания.** Не код 201 и не вид JOIN.

Сервер завис — клиент не ждёт минуту. В `fetch` — `AbortController`. На шлюзе — лимит 5–30 с. Healthcheck тоже должен отвечать быстро, иначе оркестратор решит, что процесс мёртв.

```js
const ctrl = new AbortController();
const timer = setTimeout(() => ctrl.abort(), 8000);
const response = await fetch(path, { signal: ctrl.signal, credentials: "include" });
```

### Healthcheck

Обычно **лёгкий GET**, что процесс жив. Не удаляет БД, не логинит админа и не отдаёт пароли.

```http
GET /health → 200 {"ok": true}
```

Проверяют «слушает порт», иногда «доступна БД». В учебном контракте Coral отдельного `/health` нет — идея общая для деплоя.

**На тесте:** `/users`, `Content-Type`, статика, маршрутизация, query, три стека, таймаут, healthcheck.

## 4. Сессии и безопасность

### Cookie `HttpOnly`

Недоступна из **`document.cookie` / JS**. Не «видна всему интернету», не запрет HTTPS и не localStorage.

На этапе 5 сессия лежала в `localStorage` (`coral-user`) — любой XSS её читал. На этапе 6 сервер ставит cookie сессии с HttpOnly: скрипт магазина её не видит, браузер сам прикладывает к запросам.

### `Set-Cookie` — от сервера клиенту

Заголовок **`Set-Cookie` приходит от сервера клиенту**. Не наоборот, не в CSS и не в doctype. Браузер сохраняет и в следующем запросе шлёт `Cookie: …`.

```http
HTTP/1.1 200 OK
Set-Cookie: PHPSESSID=abc; Path=/; HttpOnly
```

Клиент не «придумывает» сессию в JS. Он получает её после логина.

### Что хранит сессия

Обычно **идентификатор пользователя после логина**, не весь HTML сайта и не CSS.

```php
$_SESSION['user_id'] = $user['id'];
```

По `user_id` сервер достаёт пользователя и его заказы. В cookie — случайный id сессии, не email и не пароль.

### Пароль: хеш с солью, не в JSON

В базе хранят **хеш (с солью)**, не открытый текст, не в URL и не в заголовке `Server`.

```php
'password_hash' => password_hash($password, PASSWORD_DEFAULT)
password_verify($password, $user['password_hash'])
```

Соль внутри алгоритма (`password_hash` / Django hasher) не даёт радужным таблицам вскрыть одинаковые пароли пачкой.

Пароль в JSON-ответе API **не возвращают**. Даже «для удобства» и даже в GET-query. Публичный пользователь Coral:

```json
{ "id": 1, "name": "Ada", "email": "ada@coral.test" }
```

Поля `password` нет. Логировать пароль в access-log — **плохая практика**: лог украдут, пароль в query/`body` останется на диске. Не «обязательно PCI» и не «ускоряет login».

### Same-origin: схема, хост, порт

Same-origin включает **схему, хост и порт**. Не только путь, не имя cookie и не User-Agent.

| URL | Тот же origin, что `http://localhost:8000`? |
| --- | --- |
| `http://localhost:8000/api/me` | да |
| `http://localhost:8000/login.html` | да (другой путь) |
| `http://localhost:8001/api/me` | нет (порт) |
| `https://localhost:8000/` | нет (схема) |
| `http://127.0.0.1:8000/` | нет (хост) |

### CORS

Нужен, когда **браузерный JS с origin A ходит на origin B**. Не когда сервер ходит в БД и не Git push.

Страница на `http://localhost:8080` и `fetch("http://localhost:8000/api/products")` — разные origin. Браузер спросит сервер B заголовками `Access-Control-Allow-Origin`. В Coral PHP сам отдаёт фронт: запросы на `/api` — same-origin, CORS не нужен.

### `credentials: 'include'`

Шлёт cookie на этот URL **по правилам CORS**. Не отключает HTTPS, не кладёт пароль в query и не игнорирует 401.

```js
const init = {
  method: config.method || "GET",
  credentials: "include",
  headers: headers,
};
```

Без `include` `fetch` на другой origin не приложит cookie. На same-origin cookie сессии и так уходят; флаг в Coral ставит единообразие.

### CSRF

Эксплуатирует **автоматическую отправку cookie на чужой форме**. Не «только SQL injection» и не слабый Wi‑Fi.

Пользователь залогинен на Coral. Злой сайт показывает форму `action="http://localhost:8000/api/orders"` — браузер приложит cookie, заказ уйдёт «от имени» жертвы. Защита: CSRF-токен, `SameSite` у cookie, не делать опасные GET. JSON + `Content-Type: application/json` с чужого origin без CORS проще не пройдёт — но cookie-форму HTML это не отменяет.

**На тесте:** HttpOnly, сессия, хеш пароля, пароль не в ответе, CORS, CSRF, same-origin, credentials, логи, `Set-Cookie`.

## Как отвечать на тесте

1. Отбросьте SQL JOIN, Git, CSS, SMTP — ловушки с других этапов.
2. Ищите **роль в протоколе**: чтение vs действие, кто виноват (клиент 4xx / сервер 5xx), что хранит сессия.
3. Если вопрос про заголовок (`Content-Type`, `Set-Cookie`, `HttpOnly`) — кто его ставит и что из этого следует для JS.

После лекции: поднять один стек из `stage-06-server` (PHP :8000 проще всего), зарегистрироваться, открыть карточку, Select product — заказ переживает перезагрузку ([ДЗ этапа 6](../../06-server.md)). Сравнить ответ 401 без сессии и 409 на занятый email. Затем тест.
