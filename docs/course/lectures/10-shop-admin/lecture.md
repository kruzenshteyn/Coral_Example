Этап 10 курса. Тема теста: [Магазин: корзина, заказ, права, админка](../../tests/10-shop-admin.md) — общие правила магазина, **не** про CSS и не про Docker.

Эталон этапа: `stage-10-shop-admin/`.  
Как пройти сценарий руками: [../../guides/10-shop-admin.md](../../guides/10-shop-admin.md).

---

## Зачем эта лекция

«Выбрать товар» — не магазин. Нужны корзина с количеством, фиксация заказа (снимок цены) и разные права: покупатель и админ.

Один механизм входа (cookie-сессия этапа 6), флаг `users.is_admin`. Админ-ссылка в шапке — удобство, не защита: защиту проверяет сервер.

На тесте правильный ответ почти всегда про **кто и что может** или про **снимок заказа**, а не про DNS, минификацию и цвет кнопки.

## 1. Кто вы и что можно

Аутентификация — **кто вы (логин)**. Авторизация — **проверка прав на действие**. Не шифр диска, не цвет кнопки, не DNS, не минификация.

| Вопрос сервера | HTTP в Coral | Кто |
| --- | --- | --- |
| Вы вообще вошли? | `401` нет cookie / неверный пароль | гость |
| Вам это можно? | `403` вошёл, но не админ | обычный пользователь на админ-API |

```text
GET  /api/cart              без cookie     → 401
POST /api/admin/products    сессия Ada     → 403 Forbidden
POST /api/admin/products    admin@coral…   → 201/200 карточка
```

403 на админском POST значит: **пользователь вошёл, но не админ**. Не «сервер упал», не «товара нет», не OK.

### Наименьшие привилегии

Админ-API — **только роли админ**. Не все пользователи админы, не админ без пароля, не публичный `DROP TABLE`.

Спрятать форму CSS-ом недостаточно: `curl` всё равно пошлёт POST. В PHP это `require_admin()` после `require_user()`.

### Гость и чужая корзина

Гость **не должен читать и менять корзину без сессии**. Это не public API, CORS «всем» корзину не открывает.

Корзина привязана к `user_id`. Чужой `GET /api/cart` без вашей cookie не должен вернуть joggers Ады.

### Одна сессия, разные роли

Сессия админа и сессия покупателя — **один механизм входа, разные флаги/роли**. Не разные протоколы обязательно, не «админ без сессии», не «покупатель без HTTPS всегда».

`POST /api/auth/login` тот же. В `users` у сида `is_admin = 1` для `admin@coral.local`. `/api/me` отдаёт `isAdmin`, шапка рисует ссылку Admin. Роль живёт в БД, не в CSS.

**На тесте:** аутентификация, авторизация, гость, 403, least privilege, одна сессия.

## 2. Корзина и заказ

Корзина в отличие от заказа — **черновик, ещё не оплачен / не зафиксирован**. Не бухгалтерский учёт «всегда», не пустая, не SELECT.

```text
cart_items          черновик: user + product + quantity
orders              факт: user + created_at
order_items         снимок: title, price, quantity на момент checkout
```

### Line item — снимок

Позиция заказа хранит **снимок названия и цены на момент покупки**. Не только id без цены, не только картинку, не пароль.

Цену копируют, **потому что карточка потом может измениться**. Не потому что «SQL не умеет JOIN» и не потому что HTTP запрещает.

Админ завтра ставит Hoodie $199 — старые заказы **не должны пересчитаться**, если цена скопирована в `order_items.price`. История покупки — чек, не живая витрина.

```sql
INSERT INTO order_items (order_id, product_id, title, quantity, price)
VALUES (1, 'joggers', 'Adicolor Classics Joggers', 2, 63.85);
```

Итог заказа — **сумма (цена × количество) по позициям** (+ доставка/налоги в реальной жизни). Не случайное число, не только число SKU, не размер PNG.

`$63.85 × 2 + $130 × 1 = $257.70`

### Количество

Повторное добавление того же SKU **обычно увеличивает quantity**, не 409, не банит пользователя и не меняет PRIMARY KEY `users`.

Количество **0 удаляет строку**. Не создаёт заказ, не скидку 100%, не бан.

```text
POST /api/cart          { productId: "joggers" }           qty 1 → 2
POST /api/cart/update   { productId: "joggers", quantity: 0 }  строка исчезла
```

### Checkout

Должен **создать заказ из корзины и очистить корзину атомарно**. Не только очистить, не удалить пользователя, не сменить CSS.

Пустая корзина — **ошибка клиента (4xx)**. Не 200 с пустым заказом «всегда хорошо», не 500 обязательно, не редирект на Google. В Coral — `400 Cart is empty`.

```php
$pdo->beginTransaction();
// INSERT orders, INSERT order_items из корзины, DELETE cart_items
$pdo->commit();
```

Без транзакции легко получить «заказ без позиций» или «корзина пуста, заказа нет».

### Идемпотентность

Повтор checkout **не должен плодить два одинаковых заказа без защиты**. Не обязан создать 10 заказов, не невозможен, не «это GET».

Двойной клик «Checkout» — классика. В MVP часто достаточно: пустая корзина на втором запросе даст 4xx. В проде — ключ идемпотентности. На тесте важна идея «не два заказа».

### Сервер vs localStorage

Серверная корзина **видна с другого устройства после логина**. localStorage не безопаснее httpOnly-cookie, сервер «можно», localStorage виден не «только PHP».

Телефон и ноутбук с одним `ada@coral.local` видят одни `cart_items`.

### Статус и «мой заказ»

Статус заказа в учебном MVP **можно упростить до «создана»**. Не обязательны 15 статусов, не `:root`, не медиазапрос. В Coral у `orders` нет колонки status — сам факт строки и есть «создана».

«Мой заказ» режут запросом **`WHERE user_id = текущий`**. Не отдать все заказы всем, не поиск только по цене, не `ORDER BY random`. `GET /api/purchases` так и делает.

### Склад

Остаток (stock) в учебной модели **часто упрощают или не делают**. Не обязан законом HTML, не хранится в CSS, не viewport. В Coral колонки stock нет.

В серьёзных системах резерв при checkout — **уменьшают stock в транзакции**. Не игнорируют гонки всегда, не CSS, не `alert`. Два параллельных checkout последней единицы — гонка без `UPDATE … WHERE stock >= qty`.

**На тесте:** черновик, снимок, qty 0, checkout, пустая 4xx, итог, идемпотентность, цена не пересчитывает старое, серверная корзина, статус MVP, повтор SKU, WHERE user_id, stock.

## 3. Админка CRUD

CRUD для карточки — **Create Read Update Delete**. Не CSS Rule Utility Display и не Cookie Random UUID Data.

| Буква | В Coral |
| --- | --- |
| Create | `POST /api/admin/products` с `admin.html` |
| Read | `GET /api/products` витрина |
| Update | смена цены (идея; в MVP можно новым POST/отдельным PATCH) |
| Delete | снятие с витрины (в MVP часто не делают) |

Минимум «добавить карточку»: **непустой title и price > 0 + роль админ**. Не цвет кнопки, не favicon, не Docker.

```php
if ($title === '' || $price <= 0) {
    send_json('Title and price are required', 400, false);
}
```

Клиентскую проверку в форме обходят. Сервер — обязателен.

### URL картинки vs upload

**URL проще в учёбе; загрузка файла требует хранилища и проверок типа.** URL не «всегда безопаснее любого upload», upload не запрещён HTTP, оба в браузере работают.

В `admin.html` поле image — путь вроде `/assets/images/product-green-dress.jpg`. Не грузим байты на диск на занятии.

### Slug

Уникальный id товара — **человекочитаемый ключ + защита от коллизий**. Не пароль, не cookie, не HTTP-статус.

`Yellow Reserved Hoodie` → `yellow-reserved-hoodie-a1b2`. Два одинаковых названия не должны получить один PRIMARY KEY.

### Audit

Журнал **кто что изменил — полезная практика**. Не запрещён, не заменяет бэкап, не `SELECT` без WHERE всегда.

«Admin сменил цену joggers в 10:03» спасает при споре с покупателем. На курсе можно не делать таблицу audit — идея всё равно на тесте.

**На тесте:** CRUD, URL vs upload, slug, audit, валидация title/price + роль.

## 4. Безопасность ввода

### XSS

Название товара без экранирования — **вредоносный скрипт в админке/витрине**. Не ускорение рендера, не требование HTML, не вид JOIN.

Админ (или взломанный аккаунт) сохраняет title `<script>…</script>`. Если витрина вставит это через `innerHTML` — скрипт выполнится у всех.

Поле `description` от админа нужно **очищать / экранировать при выводе**. Не выполнять как JS, не класть в `innerHTML` без проверки, не писать в `eval`.

```js
titleNode.textContent = product.title;      // безопасно: как текст
titleNode.innerHTML = product.title;        // опасно
```

На демо лекции полезную нагрузку **показывают как текст**, не исполняют.

### CSRF

Опасен для **POST checkout / смены цены с cookie сессии**. Не для публичного GET списка товаров без побочек, не для статического CSS, не для PNG.

Браузер сам приложит cookie к POST с чужого сайта. Защита — CSRF-токен, SameSite cookie. Идея на тесте: меняющие состояние POST с сессией.

### Валидация на сервере

Валидация цены **обязательна, клиент можно обойти**. Не только в JS, не только в CSS, не «не нужна».

DevTools правит `price: -1` в JSON. Без серверной проверки в каталоге появится бесплатный товар.

**На тесте:** XSS, CSRF, серверная валидация, экранирование description; stock в учёбе упрощают (вопрос 17).

## Как отвечать на тесте

1. Отбросьте DNS, CSS, Docker, PNG — ловушки с других этапов.
2. Различайте **кто вы** (401) и **можно ли вам** (403); **черновик корзины** и **снимок заказа**.
3. Если вопрос про ввод (цена, title, description) — отвечает **сервер и экранирование**, не «форма в браузере».

После лекции: пройдите сценарий покупатель → корзина → Checkout → админ ([ДЗ этапа 10](../../10-shop-admin.md)), проверьте 401/403/400, затем тест.
